ACT 01 · 2026.09 – 2026.10 · 미래내일 일경험

흩어진 정비사업 자료를 지도 한 장에, AI는 자료만으로 답하게

문제정의 · 답이 틀릴 때 모델이 아니라 측정 장치부터 쪼갰습니다. 걸린 5건 중 4건이 검증기 문제였고, 고친 뒤 95%, 남이 쓴 50문에서 0건.

문제와 데이터

서울·경기·인천의 정비사업 자료는 기관마다 다른 형식의 엑셀, CSV, 게시판, 고시문으로 흩어져 있고 같은 사업장도 기관마다 다르게 적혀 있었습니다. 자료를 한 단위로 묶고, 검증을 통과한 것만 내보내고, AI가 자료 밖의 말을 하지 못하게 막는 장치를 만들어 두 달간 매일 운영했습니다.

↔ 좌우로 밀어서 보기
수집 → 검증 → 공개 → AI 질의 흐름. 색칠된 두 상자(검증 53항목, 검증기)가 "자료 밖의 말을 못 하게" 막는 지점입니다.

기관 5곳·수집원 17개 → 원문 컬럼은 그대로 두고 표준 컬럼을 옆에 붙임 → 같은 지번은 한 구역(중복은 1:N 보존) → 행 수·채움률·급감·연결 무결성 53항목 검증, 하나라도 실패면 중단 → 통과 때만 공개 스키마 교체, 변경 감지 요약, 실패·침묵 알림. 구역 1,922개, 사업장 레코드 1,949건, 실거래 131만 건(60개월)을 구역에 연결했고 지도 좌표 연결 91.9%는 행정동 표기가 원인임을 찾아 42곳을 보강했습니다.

평가 방법

AI는 자료가 준 값만 말합니다. 자연어를 구조화 출력으로 검색 조건에 바꾸고, 대화는 읽기 전용 도구 11개의 결과만으로 답합니다. 숫자·날짜는 검증기가 도구 결과와 대조하고 추천·전망 같은 금지 표현은 검사기가 잡아 다시 쓰게 합니다. 기능마다 정답이 있는 문항을 먼저 만들고, 자동 채점과 사람 채점을 둘 다 남겼습니다.

증명한 역량

문제정의 · 75% → 95%. 첫 평가에서 답의 숫자가 자료에 없는 비율이 25%였습니다. 프롬프트를 고치기 전에 걸린 답 5건을 뜯어 보니 4건은 모델이 아니라 검증기 문제였습니다. "2068.5만원"을 날짜로 읽고, 이어 묻는 턴에서 앞 답의 숫자를 미확인으로 잡고, 목록 번호 "1."을 숫자로 셌습니다. 측정 장치를 고치고 다시 재니 95%, 평가셋을 보지 않은 사람이 쓴 50문에서는 미확인 숫자 0건이었습니다. 숫자가 나쁘면 모델보다 측정 장치를 먼저 쪼갭니다.

AI 윤리 · 말할 수 있는 범위를 코드로. 투자 질문은 거절로 설계했다가 PM 피드백으로 "안내"로 바꿨습니다. 결론은 바꾸되 지키려던 것은 코드로 남겼습니다. 첫 문장 고정, 추천·전망 표현은 검사기가 잡아 다시 쓰게, 사실은 DB 도구 결과만. 자료에 없는 숫자는 막지 않고 "확인되지 않은 숫자"로 알립니다. 틀린 좌표 39건을 빼서 지도 표시율이 91.05%에서 89.5%로 내려간 것도, 원천 약관의 상업적 이용 금지 조항도 그대로 적어 PM이 결정하게 했습니다.

일하는 방식 · 기록해서 이어받게. PM이 준 원칙 다섯 개(원본 수정 금지, 합집합, 지역별 적재, 중복 삭제 금지, 국토부 기준)를 저장소 안내 문서 맨 위에 못 박고 두 달 지켰습니다. 설계 판단 46개를 "무엇을, 왜, 대안은"으로, 매일 로그와 운영 반영 절차를 남겼습니다. 팀원 PR은 리뷰해 머지하고 뒤따른 회귀는 제가 고쳤습니다. 의견이 밀렸을 때는 결론 대신 지키려던 것을 검사기로 바꿨습니다.

한계와 다시 한다면

기록한 사고 두 건. 경기 자료 ID 중복으로 촉진구역 40곳에 다른 사업장 이력이 이틀간 노출 → 이력 합계 테스트가 잡아 ID를 파일 행 번호로 바꾸고 중복 검증 추가. 배포 뒤 API 재시작 누락으로 20시간 동안 서울 이력이 빈 채 노출 → 운영 절차에 재시작 단계 추가. 두 건 모두 KPI 기록에 남겼습니다.

다시 한다면. 고시문 날짜 추출에서 후보를 못 찾은 70개가 더 큰 한계였으므로, 다음에는 추출 정확도보다 후보 탐색 재현율을 먼저 재는 평가를 세우겠습니다. 사고 2건은 재시작 누락처럼 절차 문제였으니 배포 체크리스트를 코드로 강제하겠습니다.

문제와 데이터

채용공고 1,190건(데이터 사이언티스트·엔지니어·ML 엔지니어·데이터 분석가)에서 요구 역량을 뽑는 일은 LLM에 맡기면 결과가 바로 나옵니다. 문제는 그 결과가 맞는지 확인할 방법이 없다는 점입니다. 역량 사전 106 canonical / 288 alias를 만들고, 공고 38건을 사람이 판정한 정답셋을 먼저 세웠습니다.

평가 방법

정규식 베이스라인과 Claude haiku·sonnet·opus를 같은 정답셋으로 채점합니다. 정답셋은 네 시스템의 후보를 출처를 가리고 섞어 판정했고(블라인드 풀링), 방식 간 차이는 공고 단위 부트스트랩 10,000회의 짝지은 차이 신뢰구간으로만 말합니다. 프롬프트 실험은 변형과 판정 기준을 실행 전에 문서로 고정해 커밋하고 각 1회만 돌렸습니다. 모든 표는 make reproduce 한 줄로 바이트 단위 재현되고 GitHub Actions가 매 push 검증합니다.

증명한 역량

문제정의 · 결함 4회. 첫 정답셋은 정규식 출력을 사람이 확인하는 방식이라, 정규식이 못 본 태그는 정답에 없었습니다. "어느 모델이 낫나"를 묻기 전에 "이 정답셋을 믿을 수 있나"를 먼저 물었고, 네 시스템의 후보를 출처를 가리고 섞어 다시 판정했습니다(후보 439건 중 127건 제외, 정규식-LLM 격차 0.091 → 0.024). 이어서 풀링 누락, 사전 충돌과 함의 규칙 부재, 잘린 응답까지 네 번 모두 추출기가 아니라 채점기·정답셋·예측 파일의 문제였습니다. 결론은 두 번 바뀌었고, 바뀐 결론을 그대로 썼습니다.

AI 윤리 · 확정되지 않은 것은 쓰지 않음. 라우팅 시뮬레이션은 무작위 대비 +1.1σ라 "작동한다"고 쓰지 않았습니다. 프롬프트 변형 3개는 판정 기준을 실행 전에 커밋하고 각 1회만 돌렸으며, 셋 다 점추정이 내려간 결과를 그대로 공개했습니다. 정답셋 2차 확장(후보 208건)은 판정이 성급했음을 스스로 확인해 폐기했습니다.

일하는 방식 · 재현 가능하게. 정답셋 38건을 직접 판정하고 전 과정을 커밋했습니다. 모든 표는 make reproduce 한 줄로 바이트 단위 재현되고 GitHub Actions가 매 push 검증하며, 데모는 커밋된 CSV만 읽어 README와 숫자가 같습니다. 테스트 84건.

한계와 다시 한다면

정답셋 38건은 어떤 순위도 확정하기에 작습니다. 정답셋 2차 확장(후보 208건)은 판정이 성급했음을 스스로 확인해 폐기했고, 레포는 38건을 유지합니다. 네 번째 결함(잘린 응답)은 예측 파일 쪽을 한 번도 의심하지 않아서 생겼습니다.

문제와 데이터

무신사 랭킹을 Selenium으로 수집하고 공휴일 API와 함께 BigQuery에 적재한 뒤 두 경로로 썼습니다. 하나는 Claude Desktop에서 자연어로 BigQuery를 질의하는 MCP 서버, 다른 하나는 GA 공개 고객 데이터 9,996명의 RFM 등급 예측입니다. 두 데이터는 조인되지 않은 별도 파이프라인입니다.

평가 방법

RFM 4등급(VIP 17.5% · 우수 38.2% · 일반 36.1% · 이탈위험 8.2%)을 RF·XGBoost로 예측하고, 전체 정확도가 아니라 등급별 재현율로 판단했습니다. MCP 서버는 SELECT 전용, 다중 구문 차단, LIMIT 자동 부착의 가드 3줄을 두고 툴 3개(list_tables · get_schema · run_query)만 노출합니다.

결과

보정 전 정확도 98.5%는 클래스 불균형이 만든 착시였고 우수고객 재현율은 6%였습니다. 클래스 가중치 보정으로 재현율 94%까지 올렸고, 우수고객의 VIP 전환이 가장 큰 지렛대라는 결론을 냈습니다.

증명한 역량

문제정의 · 98.5% → 6%. 정확도 98.5%에서 멈추지 않고 등급별로 쪼개 보니 우수고객 재현율이 6%였습니다. 지표를 전체 정확도에서 소수 등급 재현율로 바꾸고 클래스 가중치를 보정해 94%까지 올렸습니다. XGBoost 조기 종료가 테스트 세트를 보고 있어 95.4%는 낙관적이라는 점도 README에 적었습니다.

한계와 다시 한다면
  • 등급 라벨을 RFM 피처로 다시 예측하는 순환 구조입니다. 타겟을 미래 행동(재구매·이탈)으로 바꾸는 것이 근본 개선입니다.
  • XGBoost 조기 종료가 테스트 세트를 보고 있어 95.4%는 낙관적인 값입니다. README에 적었습니다.
  • 무신사 상품 데이터와 GA 고객 데이터는 조인되지 않은 별도 파이프라인입니다.
다시 한다면. 타겟을 RFM 등급이 아니라 "다음 달 재구매 여부"로 정의해 순환을 끊고, 검증 세트를 따로 떼어 조기 종료에 쓰겠습니다. MCP 서버에는 쿼리 비용 상한과 호출 로그를 넣겠습니다.
